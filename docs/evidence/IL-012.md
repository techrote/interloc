## Implemented scope

The branch adds a bounded experiment package under `experiments/capture/` plus the manual native matrix:

- deterministic Tk fixture with high-contrast geometry and a changing marker for stale-frame detection;
- deterministic local WebGL2 fixture with no network dependencies;
- standard-library `PrintWindow` comparator that accepts one exact HWND or a uniquely matching exact title, validates an optional expected PID, rejects dimensions outside 4096x4096, emits BMP/hash/metadata, and never falls back to desktop capture;
- `run_case.py` supervisor that uses fixed local helpers, enforces a maximum 10-second capture timeout, limits accepted BMP size, hashes outputs, and refuses to write capture evidence inside the source worktree;
- narrow C++/WinRT Windows Graphics Capture prototype that creates a `GraphicsCaptureItem` for one supplied HWND, uses D3D11, waits for one frame with a bounded timeout, revalidates PID, enforces 4096x4096, and writes BMP;
- explicit build helper requiring Visual C++ Build Tools plus a current Windows SDK; no Python runtime/dependency-lock change;
- reproducible PASS/FAIL/UNSUPPORTED/NOT-RUN matrix for synthetic, Windows Terminal and GPU targets across visibility, occlusion, minimization, DPI, multi-monitor and access-failure cases.

## Non-goals

No production capture provider, broker/schema/runtime wiring, consent UI, PNG encoder, remote image delivery, monitor capture, desktop fallback, active-window guessing, OCR, keyboard/mouse automation, privilege escalation, or screenshot publication. The source repository contains only synthetic fixture/code/documentation; real captures remain local.

## Backend research

Primary Microsoft documentation was rechecked on 2026-09-13:

1. `IGraphicsCaptureItemInterop::CreateForWindow` — https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow
   - targets a single HWND;
   - minimum supported client/server is Windows 10 version 1903 (build 18362).

2. Windows screen capture overview — https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture
   - `Windows.Graphics.Capture` acquires frames from an application window/display;
   - support must be checked at runtime and capture has user-visible/system semantics.

3. `PrintWindow` — https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow
   - copies a visual window into a supplied device context;
   - is synchronous/blocking;
   - the owning application processes the request and renders the image.

These documents justify the candidate set and harness design; they do **not** establish behavior for minimized, protected, elevated, terminal or GPU-rendered targets on the user's machine.

## Provisional design status

WGC is the primary candidate because it has a documented direct-window interop path. It is **not selected yet**. `PrintWindow` is retained as a dependency-free comparator because its application-rendering semantics may fail differently for modern composited/GPU applications. No backend is allowed to recover from scoped failure by capturing a monitor or the desktop.

Desktop Duplication / monitor-capture-and-crop was not promoted as a candidate: it begins with monitor output and therefore expands the privacy blast radius beyond the required exact-window capability. A future candidate would need its own issue/evidence amendment rather than silent substitution.

## Security review

The harness deliberately keeps the production security boundary visible:

- exact scoped target only; no whole-desktop fallback exists in either probe;
- exact-title lookup is experiment convenience only and fails on zero/multiple matches; production IL-013 still requires opaque IDs bound to process creation identity/session/scope;
- expected PID can be revalidated before/after capture; stale/reused handle cases remain explicit native tests;
- samples are prevented by the supervisor from being written under the source worktree;
- the `PrintWindow` blocking call is isolated in a child process and supervised by a hard experiment timeout;
- WGC has its own bounded first-frame wait;
- helpers receive no GitHub/broker credentials and have no publication function;
- image content is not declared safe merely because dimensions/hash are valid; local human content validation remains required.

## Packaging consequences

`PrintWindow` requires only Windows system APIs from Python/ctypes but may have weaker behavior on modern composited/GPU windows. WGC requires a native Direct3D/C++/WinRT helper in this prototype. Building it requires MSVC/Windows SDK; that is acceptable for feasibility work but is not an acceptable end-user runtime prerequisite. If WGC wins the native matrix, IL-013/IL-024 must specify a versioned prebuilt/signed helper or another reproducible packaging solution and test clean no-admin installation.

No `pyproject.toml` or dependency lock was changed by this work.
